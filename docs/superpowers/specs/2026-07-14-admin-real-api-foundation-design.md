# SaaSBase 前端 admin 真实 API 基础设计

## 目标

为 `admin` 管理端建立真实 API 接入的第一阶段基础，覆盖认证、用户、部门三条主链路，并提供一个混合式工作台首屏。

本阶段要做到：

- 登录态可进入租户后台
- 用户列表、详情、状态操作、重置密码等能力能接到真实后端
- 部门树、成员列表、移动、启用、停用、删除等能力能接到真实后端
- 页面结构、权限边界和错误处理保持清晰

## 范围

包含：

- `admin` 登录页与认证流
- 路由守卫和权限拦截
- 租户工作台首屏
- 用户列表、详情、启用、停用、重置密码、转部门
- 部门树、成员列表、启用、停用、删除、移动
- 模块级 API 封装与类型适配
- 页面级 loading、empty、error、无权限状态

不包含：

- 文件模块
- 平台租户管理
- portal 官网
- 生产部署与 CI/CD 配置
- 后端接口变更本身

## 架构

```text
apps/admin
├── src/modules/auth
├── src/modules/dashboard
├── src/modules/users
├── src/modules/depts
├── src/router
├── src/layouts
└── src/api
```

### 布局

采用固定侧边栏 + 顶部信息条 + 内容区的混合式工作台布局。首屏先展示租户概览和快捷入口，再把用户与部门工作流放入独立模块。

### 模块边界

- `auth`：登录、退出、会话维护和权限守卫需要的最小状态
- `dashboard`：工作台首屏概览和快捷入口
- `users`：用户列表、详情与用户操作
- `depts`：部门树、成员列表与组织操作
- `api`：只做后端接口的轻封装，不堆放页面逻辑

### 数据流

- 进入应用先检查会话
- 登录成功后进入工作台
- 用户、部门页面各自从 `api` 层取数
- 写操作完成后刷新当前视图的查询条件

## 路由

- `/login`：登录页
- `/`：工作台首屏
- `/users`：用户列表
- `/users/:id`：用户详情
- `/depts`：部门树与成员列表
- `/forbidden`：无权限页
- `/:pathMatch(.*)*`：404 页

路由元信息用于声明访问权限，但前端权限控制只作为体验层，最终授权仍以后端为准。

## API 接入边界

### 认证

- 登录、刷新、退出使用统一认证模块
- 不在业务页面直接读写 token
- 认证失效后清理内存会话并跳转登录页

### 用户

- 列表分页使用后端的 `page`、`size`
- 筛选字段与后端契约一一对应
- 详情、启用、停用、重置密码、转部门都挂在同一资源下的子路径

### 部门

- 部门树使用 `/tree`
- 成员列表使用 `/{deptId}/members`
- 删除、启用、停用、移动等操作保留后端要求的版本或命令对象

### 共享契约

- 优先复用 `packages/api-client`
- 只在 `admin` 内做轻量适配，不重复定义 DTO

## 错误处理

- 认证失效：清理会话并跳转登录页
- 权限不足：进入无权限页
- 资源不存在：展示明确的 404 或空状态
- 版本冲突：提示用户刷新后重试
- 表单校验失败：保留字段级错误信息
- 其他后端错误：保留 `code` 和 `message`

## 测试与质量门禁

- 共享契约层继续保持单元测试
- `admin` 的路由守卫、认证流、用户列表和部门树需要单元测试或组合测试
- 关键路径补 Playwright E2E：登录、未登录跳转、权限拦截、用户列表、部门树
- 每次修改至少运行受影响的测试，再补全 lint、typecheck、build

## 完成标准

当以下条件全部满足时，本阶段可视为完成：

- `admin` 已能真实登录并进入工作台
- 用户与部门两条链路已经接到后端
- 路由守卫和错误页工作正常
- 页面具备 loading、empty、error 和无权限状态
- 类型与测试覆盖了核心交互

## Agent Prompt Guide

- 先做认证、用户、部门这条主链路
- 页面先清楚，再补复杂度
- 不要把文件模块或平台租户塞进这一阶段
- 不要手写重复 DTO，优先复用 `packages/api-client`
